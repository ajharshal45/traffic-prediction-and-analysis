[68] [Heading 1] 1. Introduction
[69] [Heading 2] 1.1 Purpose
[70] [Normal] This document specifies the software requirements for the CA Firm Attendance and Article Management System, Version 1.0. The system is a web-based platform developed for SPCM (Chartered Accountant Firm) that digitizes and automates the management of article trainees in the firm.
[71] [Normal] The system provides digital attendance tracking with biometric face recognition and GPS-based location verification, task assignment and management, real-time progress tracking, leave management, automated reporting, and performance monitoring. Future enhancements include AI-based performance analysis and a dedicated mobile application.
[72] [Normal] This SRS covers the complete system comprising a React.js frontend, Node.js Express backend, MySQL database, and Python-based face recognition microservice.
[73] [Heading 2] 1.2 Document Conventions
[74] [Normal] This document follows these typographical conventions:
[75] [List Bullet] Bold text indicates requirement IDs (e.g., REQ-AUTH-1).
[76] [List Bullet] SHALL indicates a mandatory requirement implemented in the current version.
[77] [List Bullet] SHOULD indicates a feature that is recommended and planned for future phases.
[78] [List Bullet] Higher-level feature priorities are inherited by all child functional requirements unless overridden.
[79] [List Bullet] All requirement IDs are unique and follow the format REQ-<MODULE>-<NUMBER>.

The software replaces traditional paper-based management of article trainees with a comprehensive digital platform.

[109] [Heading 1] 2. Overall Description
[110] [Heading 2] 2.1 Product Perspective
[111] [Normal] The CA Firm Attendance and Article Management System is a new, self-contained web application designed to replace traditional manual systems used in Chartered Accountant firms for managing article trainees. It is not a replacement of any existing software product. The system operates as a three-tier client-server architecture:
[112] [List Bullet] Presentation Layer (Frontend) — React.js SPA with responsive design for desktop and mobile browsers
[113] [List Bullet] Application Layer (Backend) — Node.js with Express.js RESTful API server handling business logic
[114] [List Bullet] Data Layer (Database) — MySQL relational database for structured data storage with referential integrity
[115] [List Bullet] Face Recognition Service — Python-based microservice using face-api.js/OpenCV for biometric attendance verification
[116] [Normal] The system uses JWT-based authentication, bcrypt password hashing, and role-based access control to ensure security. GPS coordinates from the browser Geolocation API verify physical presence during attendance marking.

[194] [Heading 2] 4.1 User Authentication and Session Management
[195] [Heading 3] 4.1.1 Description and Priority
[196] [Normal] Priority: High
[197] [Normal] Provides secure login and logout for Admin (CA) and Article (Trainee) users. Implements JWT-based authentication with role-based access control. Includes password reset functionality and automatic session expiration for security.
[198] [Heading 3] 4.1.2 Stimulus/Response Sequences
[199] [List Bullet] User navigates to Login page -> enters username and password -> system verifies credentials -> checks user type (Admin/Article) -> issues JWT token -> redirects to appropriate dashboard
[200] [List Bullet] User clicks Logout -> system invalidates JWT token/clears cookie -> redirects to Login page
[201] [List Bullet] User requests password reset -> system sends reset link via email -> user sets new password
[202] [List Bullet] Session expires after inactivity period -> system redirects to Login page with session expired message
[203] [Heading 3] 4.1.3 Functional Requirements
[204] [Normal] REQ-AUTH-1: The system shall provide separate login functionality for Admin and Article users with username and password.
[205] [Normal] REQ-AUTH-2: The system shall authenticate users using JWT tokens with configurable expiration (default: 24 hours).
[206] [Normal] REQ-AUTH-3: The system shall implement role-based access control (RBAC) with Admin and Article roles.
[207] [Normal] REQ-AUTH-4: The system shall hash all passwords using bcrypt with a minimum of 10 salt rounds before storage.
[208] [Normal] REQ-AUTH-5: The system shall display appropriate error messages for invalid login credentials.
[209] [Normal] REQ-AUTH-6: The system shall provide secure logout functionality that terminates the user session.
[210] [Normal] REQ-AUTH-7: The system shall provide password reset functionality via email verification.
[211] [Normal] REQ-AUTH-8: The system shall automatically expire sessions after a configurable inactivity timeout (default: 30 minutes).
[212] [Normal] REQ-AUTH-9: The system shall prevent concurrent login from multiple devices for the same account.

[230] [Heading 2] 4.3 Attendance Management (Biometric Face Recognition + GPS)
[231] [Heading 3] 4.3.1 Description and Priority
[232] [Normal] Priority: High
[233] [Normal] Core attendance module implementing dual-factor verification: biometric face recognition using the device camera and GPS-based location verification using the browser Geolocation API. Ensures fraud-proof attendance by verifying both identity (face match) and physical presence (GPS within geofenced office radius). Admin can view and generate attendance reports.
[234] [Heading 3] 4.3.2 Stimulus/Response Sequences
[235] [List Bullet] Article opens Attendance page -> system requests camera permission -> captures live face image -> face-api.js compares with registered face descriptor -> if match confirmed, proceeds to GPS check
[236] [List Bullet] System requests GPS permission -> retrieves device coordinates -> calculates distance from office location using Haversine formula -> if within geofence radius (100m), attendance marked -> date and time recorded automatically
[237] [List Bullet] If face does not match -> attendance denied with 'Face verification failed' message
[238] [List Bullet] If GPS location outside geofence -> attendance denied with 'You are not at the office location' message
[239] [List Bullet] Admin views daily/monthly attendance -> system retrieves records from database -> displays in tabular format with export option
[240] [Heading 3] 4.3.3 Functional Requirements
[241] [Normal] REQ-ATT-1: The system shall allow article trainees to mark attendance using biometric face recognition via device camera.
[242] [Normal] REQ-ATT-2: The system shall capture a live face image and compare it against the registered face descriptor using face-api.js with a minimum confidence threshold of 0.6 (60%).
[243] [Normal] REQ-ATT-3: The system shall verify GPS location using the browser Geolocation API before confirming attendance.
[244] [Normal] REQ-ATT-4: The system shall implement geofencing with a configurable radius (default: 100m) from the preconfigured office coordinates.
[245] [Normal] REQ-ATT-5: The system shall calculate distance from office using the Haversine formula.
[246] [Normal] REQ-ATT-6: The system shall automatically record the date and time when attendance is marked.
[247] [Normal] REQ-ATT-7: The system shall enforce a one-attendance-per-day policy per article trainee.
[248] [Normal] REQ-ATT-8: The system shall store attendance records with article ID, date, time, GPS coordinates, face match confidence score, and status (Present/Absent/Late).
[249] [Normal] REQ-ATT-9: The system shall allow Admin to view daily and monthly attendance records for all articles.
[250] [Normal] REQ-ATT-10: The system shall generate exportable attendance reports (PDF/CSV) for selected date ranges.
[251] [Normal] REQ-ATT-11: The system shall support marking check-in and check-out times to calculate working hours.
[252] [Normal] REQ-ATT-12: The system shall display attendance summary statistics (present days, absent days, late arrivals, average working hours) per article.

[434] [Normal] Data Flow — Attendance Marking:
[435] [Normal] 1. Article opens Attendance page -> Frontend requests camera access
2. Live face image captured via browser MediaDevices API
3. face-api.js processes image -> extracts face descriptor vector
4. Descriptor compared against registered face data (Euclidean distance, threshold: 0.6)
5. If face match: Frontend requests GPS coordinates via Geolocation API
6. Coordinates sent to Backend -> Haversine distance calculated from office location
7. If within geofence radius (100m): Attendance record created with timestamp
8. Backend stores: article_id, date, time, GPS coords, face confidence, status
9. Success response -> Frontend displays 'Attendance Marked Successfully'
[436] [Normal] 
[437] [Normal] Data Flow — Task Assignment:
[438] [Normal] 1. Admin creates task (title, description, deadline, priority, category)
2. Admin selects articles(s) for assignment
3. Backend creates task record and assignment records in database
4. Notification sent to assigned article(s) via email and in-app notification
5. Article views task on dashboard -> updates progress -> Backend updates record
6. When 100% -> Backend marks task complete -> notifies Admin
